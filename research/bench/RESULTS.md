## A. The two walls

A1. Pigeonhole. A state of W bits has 2^W values; more than 2^W distinct histories must
    collide, and colliding histories exist that need different answers. Bounded state =>
    lossless unbounded recall is impossible. No design escapes this.

| W (bits) | states 2^W | tokens until collision floor at 1 bit/token |
|---|---|---|
| 16 | 6.554e+04 | 65,536 |
| 24 | 1.678e+07 | 16,777,216 |
| 32 | 4.295e+09 | 4,294,967,296 |
| 40 | 1.100e+12 | 1,099,511,627,776 |
| 48 | 2.815e+14 | 281,474,976,710,656 |
| 64 | 1.845e+19 | 18,446,744,073,709,551,616 |

A2. Energy. q independent queries over an answer set of size S need >= q*log2(S) bits
    of *somewhere* -- working RAM, or an addressable store.

| queries q | answer set S | bits required | KiB |
|---|---|---|---|
| 1,000 | 50,000 | 1.561e+04 | 1.905e+00 |
| 100,000 | 50,000 | 1.561e+06 | 1.905e+02 |
| 1,000,000 | 50,000 | 1.561e+07 | 1.905e+03 |

    Read together: RAM must stay O(1) (R2), so the bits live in the store, so the only
    honest claim is *constant working state*, and the measured question becomes cost per
    generated token (G4). A primitive whose per-token reads grow is attention renamed.

## D4 [post-hoc]. Does sharing the operation table across positions buy composition?

y=(a+b) mod 100. One shared table over (digit_a, digit_b, carry), applied recursively
over 2 positions. Train only on a,b < 16 (256 pairs).

| model | table entries | seen acc | held-out correct | **held-out WRONG** | abstain |
|---|---|---|---|---|---|
| shared table, recursive | 104 | 100.0% | 55.7% | **0** / 9744 | 44.3% |

    Precision on everything it answers: 100.0%. It never guessed wrong.
    Compare D2 (one table per operand pair, 10000 rows, unshared): held-out 11.8%,
    and every unseen row is a confident wrong answer. Same closed-form trainer, same task,
    10000 rows -> 104 rows, and the failure mode changed from *silent wrong* to
    *locally-attributable abstention*.

    So the axis is not trainer, capacity, or regularisation: it is **parameter sharing
    across positions/roles**, which also makes the model's incompetence *enumerable*.
    A three-way outcome (correct / wrong / abstain-with-cause) is a capability a softmax
    Transformer cannot express at all, and it is measurable. Adopt it as G8 (see charter).

## VERDICT ON THREAD 0002's K3 CONTROL

**0.1% was a defect in the measuring instrument, not a fact about the task and not a
finding about difficulty.** Three concrete defects (BUG-1, BUG-2, BUG-3), each of which
alone is enough to make every method look dead. None of them is fixed by tuning a model.

* The task IS learnable. IN-SPLIT, with all digit values observed and only pairs held
  out, the counted role table reaches 100.00% exact and backprop-one-hot reaches
  29.2% exact (96.9% on the units digit alone).
  "The task was too small for anyone" is therefore false as stated.
* 0.1% is exactly 1/1000 -- chance. On a population whose symbols never appeared in
  training, chance is the only available score for a symbol-blind learner, so the
  number carries no information about task size, model quality, or the primitive.
* What the corrected harness DOES find is a real difference, and it is not accuracy:
  under an unseen-symbol split the counted table answers NOTHING WRONG (it abstains),
  while backprop-one-hot is confidently wrong on essentially every scored item. That is
  G8 -- calibrated abstention -- measured against a same-data, larger-parameter baseline
  for the first time. Coverage and precision must be read separately; a table that
  abstains is not beaten by a model that guesses.

observed is answered exactly by that automaton at any depth, by construction. Therefore
**no composition-depth test on this task family can distinguish a table from an
algebra**, and three falsifiers in a row could not fail because the task cannot fail
one. The defect is in the task family, not in the three threads.

## 3. What a discriminating test has to look like

To separate 'a table with the local map' from 'a representation closed under
composition', the task must require state that grows with depth. The measurable
signature is the middle column above: a **key count that grows with depth**.
Addition's stays at 104. A task whose key count grows -- reversal, Dyck-language
matching, unbounded-counter arithmetic -- costs a lookup table entries proportional to
depth, while a compositional representation need not grow at all. That is the only
shape of test that can kill something here.

This is a statement about *tasks*, not about primitives: the Builder is not proposing a
candidate, only the instrument. It also fixes what K1 and K2 must be run on.

# Part 12 -- G7 had no instrument; it has one now, and it says the gate is nearly free to pass (turn 9)

Part 10 ended with a promise this part keeps: *a direct-address store gives every key one slot,
so one edit can damage at most the slot population. To measure collateral honestly the harness

## 12.1 The instrument

One **superposed vector** holds every binding: `s = sum_k psi(v_k) * phi(k)`, with ±1 key
codes and 16-block ±1 value codes. A GET unbinds one key (`s * phi(q)`) and decodes sixteen
block means. The property that matters is that **every write touches the memory every key
reads**, so an edit can damage keys it never named -- which is what G7 is about and what no
slot-per-key store can exhibit.

Three update rules are measured, because the edit is the event under test and a collateral
column has to change when the event changes:

* **add** -- `s += psi(new) * phi(k)`; the old binding survives as a ghost.
* **oracle** -- erase the *true* old value, then add. This is the best an edit can do.
* **recalled** -- erase what the machine *recalled* before the edit. This is what it can
  actually do, and at load it subtracts a wrong codeword.

**51.25%** and **49.38%** with 32,768 bits -- four hundred and seventy-five times the state
and no better than the 0-parameter rows. That is not a claim that learning fails on Dyck-2; the
Elman rows reach 73% at `D=4` and the curriculum row shows why. It is a claim about what bits
buy: **bits are not the currency, organization is.** A table with 32,768 cells cannot count to
64, because counting is not in the hypothesis class however finely the cells are cut.

The useful consequence is a scoring rule. `AMEND-006` caps working state at 2^30 bits and
`stack@D=64` needs 69, so *capacity* is never the objection to a candidate here -- and a
candidate that answers `D>=32` by carrying a bigger table is now measurable against a baseline
that already has one. What a candidate has to show is a mechanism, not a budget.

## 14.3 Task B: at matched bits the learned baseline *wins* one hop and loses the composition

One-hop binding, same stream, same bytes:

| n | machine | bits | coverage | edit collateral | bytes read/token | G4 |
|---|---|---|---|---|---|---|
| 1,000 | LEARNED byte table (hashed) | 32,768 | 100.00% | 0 | 2 | yes |
| 1,000 | direct 1024 (ORACLE OPCODE) | 16,384 | 100.00% | -- | 2.7 | yes |
| 10,000 | LEARNED byte table (hashed) | 32,768 | 20.10% | 0 | 2 | yes |
| 10,000 | direct 1024 (ORACLE OPCODE) | 16,384 | 9.20% | -- | 3.7 | yes |

At `n=10,000` the 32,768-bit learned table answers **20.10%** against the
16,384-bit oracle store's **9.20%** -- half the bits and more than twice the
coverage, because 2,048 hashed buckets spread 10,000 keys better than 1,024 slots taken modulo
an adversarial key set. So the honest bar for this task is *not* `m/n`: any design that only
matches a 1,024-slot store at 16,384 bits has not beaten a two-line learned baseline.

`GET2` is where that baseline dies, and where the pigeonhole bound does the work:

| n | machine | GET2 coverage | ceiling | bytes read/token | G4 |
|---|---|---|---|---|---|
| 1,000 | direct 1024 (2 hops) | 100.00% | 1.0000 | 2.0 | yes |
| 1,000 | KV scan | 100.00% | 1.0000 | 4,000 | **no** |
| 1,000 | LEARNED byte table (2 hops) | 67.30% | -- | 4 | yes |
| 10,000 | direct 1024 (2 hops) | 1.07% | 0.0105 | 2.0 | yes |
| 10,000 | KV scan | 100.00% | 1.0000 | 40,000 | **no** |
| 10,000 | LEARNED byte table (2 hops) | 0.03% | -- | 4 | yes |

The oracle store lands on its ceiling -- **1.07%** measured against
**1.05%** -- because two hops square the per-hop loss, and the learned
table gets **0.03%**, far below even that, because its collisions are not uniform.
Only the KV scan is exact, at **40,000 bytes/token**: ten times the 4 KiB budget, which
is G4's whole point. Composition is the headroom `AMEND-008` asked to see, and what it shows is
that no fixed-budget store escapes `(m/n)^k` by being clever -- only by being exact.

## 14.4 Four instruments built, published inside this part, and thrown away

Every number in 14.2-14.3 came after an instrument that lied in a *different* direction. They are
listed because three of the four would have made a store look better than it is, and the ceiling
is the only thing that caught them:

| # | what I built | what it reported | what was wrong | what caught it |
|---|---|---|---|---|
| 1 | queries drawn as `keys[:k]` | 0.00% learned coverage at `n=10,000` | the first `k` keys are the earliest writes, so they are exactly the ones a collision overwrites; measures write order, not coverage | the number was *too low* for the pigeonhole (`2,048/10,000 = 20%`) -- same error as the direct store in turn 8 |
| 2 | `GET2` over a cycle `a->b->a` | 0.40% for the learned table | the chain returned the query itself, so the composition was never exercised | the oracle row read 65% against a 1% ceiling |
| 3 | edit value reused from `C` | 65.20% for the oracle store | two `B` keys mapped to one `C` value, so a wrong link matched a wrong link | same ceiling check |
| 4 | `A` in order, both hops paired by index | 5.50% for the oracle store | a dict's write order *is* insertion order, so 'last writer' meant 'largest index' in both hops, correlating them | ceiling 1.05%, and it did not move when `A` was shuffled -- the pairing, not the shuffling, was the bug |

The pattern: a benchmark that reports *below* its own bound is as broken as one that reports
above it, and only an independently derived bound distinguishes the two. `AMEND-007`'s
pigeonhole requirement is what made these four findable.

## 14.5 Audit of this part

**Certified:** `C17` recomputes the four numbers this part rests on -- the 69/32,768-bit split
on A2 (`D=64` exact for the oracle, not for the learned table), the learned-beats-oracle one-hop

every `B`. `dyck2.py` was re-run twice and `stream_ram.py` twice; both pairs are identical

**Not claimed:** that no learned system can pass A2 -- one mechanism (a differentiable counter)

**What would prove this wrong:** a learned model under 4,096 bytes of state that stays above

## 15.1 What changed

1. **G7 does not bite on a correct edit.** Every exact store answers 100% after the edit with 0
